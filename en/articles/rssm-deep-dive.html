Deep Dive into RSSM: The Core Engine of World Models

August 2, 2026 · ~15 min read · RSSM, State-Space Model, DreamerV3

In the previous article, we covered the basic concepts of world models and the overall architecture of DreamerV3. Some readers asked for a deeper look at how RSSM actually works under the hood. This article breaks down the core component that powers the Dreamer family of world models.

I'll walk through the math as clearly as possible, but without excessive formalism. After all, our goal is to understand the principles, not prove theorems.

Why Do We Need a State-Space Model?

Before discussing RSSM, let's take a step back and ask: why do we need a state-space model at all? Can't we just use a plain RNN or Transformer?

Consider RNNs first. The problem with traditional RNNs is that they compress all information into a single deterministic hidden state vector. It's like asking you to describe "how's the weather today" using a single number — no matter how you choose that number, you'll lose a tremendous amount of information. More critically, RNNs have no way to express uncertainty. If the environment has stochastic elements (say, a gust of wind), an RNN cannot express "I'm not sure what's going to happen next."

Now consider Transformers. The attention mechanism is certainly powerful, but it comes with two issues: first, computational complexity grows quadratically with sequence length, which is prohibitively expensive for robotic tasks that require long-range memory; second, it is fundamentally an open-loop model with no explicit state transition structure, making it ill-suited for control.

A state-space model (SSM) offers a middle ground. It has an explicit state transition equation that captures the essence of dynamical systems, while carefully designed state representations strike a balance between expressiveness and computational efficiency.

The Core Idea of RSSM: Dual-Track State

RSSM stands for Recurrent State-Space Model. Its key innovation is splitting the hidden state into two tracks:

Deterministic State hₜ

This state is analogous to the hidden state of a traditional RNN, updated via a GRU (Gated Recurrent Unit):

hₜ = GRU(hₜ₋₁, zₜ₋₁, aₜ₋₁)

It captures the deterministic dynamics of the environment — the parts that can be predicted precisely. For example, "if the robot arm moves 10 cm to the right, the end-effector's x-coordinate increases by 10 cm" — a deterministic physical relationship.

Stochastic State zₜ

This state is sampled from a distribution:

zₜ ~ p(zₜ | hₜ)     # prior (during imagination)
zₜ ~ q(zₜ | hₜ, oₜ)  # posterior (during training)

It captures the uncertainty in the environment — the parts that cannot be predicted precisely. For example, "the friction coefficient between two surfaces may be anywhere from 0.2 to 0.4" — an inherently ambiguous physical property.

Why split the state this way? Because the real world is governed by both deterministic laws and stochastic factors. By modeling them separately, the model can form a more accurate understanding of the environment.

The Complete State Transition Process

Let's walk through the RSSM state transition step by step. Suppose at time step t we have an observation oₜ (e.g., a camera image) and an action aₜ (e.g., joint torques):

Step 1: Update the deterministic state

hₜ = GRU(hₜ₋₁, zₜ₋₁, aₜ₋₁)

We concatenate the previous deterministic state hₜ₋₁, the stochastic state zₜ₋₁, and the action aₜ₋₁, then pass them through the GRU to obtain the new deterministic state. This step is analogous to a traditional RNN update.

Step 2: Compute the stochastic state

There are two modes here:

During training (with real observations), we use the posterior distribution:

μₜ, σₜ = Encoder(hₜ, oₜ)
zₜ = μₜ + σₜ * ε,  where ε ~ N(0, I)

During inference (no real observations, during imagination), we use the prior distribution:

μₜ, σₜ = Prior(hₜ)
zₜ = μₜ + σₜ * ε,  where ε ~ N(0, I)

This design is quite elegant. During training, the posterior distribution leverages real observations to correct predictions, improving training efficiency. During inference, only the prior distribution is used, allowing the model to make predictions purely based on its internal state without requiring external observations.

Step 3: Decode outputs

Given the state (hₜ, zₜ), we can decode various outputs:

Observation prediction: ôₜ = Decoder(hₜ, zₜ)
Reward prediction: r̂ₜ = RewardHead(hₜ, zₜ)
Discount prediction: γ̂ₜ = DiscountHead(hₜ, zₜ)

Training Loss

The RSSM training loss consists of three components:

1. Reconstruction Loss

L_recon = -log p(oₜ | hₜ, zₜ)

This drives the model's predicted observations to match the real observations as closely as possible, pushing the model to learn the environment dynamics.

2. KL Divergence Loss

L_kl = KL[q(zₜ|hₜ,oₜ) || p(zₜ|hₜ)]

This pushes the posterior distribution close to the prior distribution. The purpose of this loss is to ensure that the model performs well during inference (when only the prior is available). Without this constraint, the posterior and prior could diverge significantly, leading to good training performance but collapsed inference.

In practice, the KL divergence is typically scaled by a coefficient, and the "free bits" trick is applied — when the KL falls below a certain threshold (e.g., 3 nats), no further penalty is imposed, preventing the model from over-compressing information.

3. Reward / Discount Loss

L_reward = -log p(rₜ | hₜ, zₜ)
L_discount = -log p(γₜ | hₜ, zₜ)

This ensures the model accurately predicts rewards and termination conditions.

Physics-Aware RSSM: An Improvement Direction

The standard RSSM treats the state as a "black-box" vector, without regard for whether it corresponds to real physical quantities. However, in robotic tasks, many states have clear physical meanings — position, velocity, force, temperature, and so on.

A natural direction for improvement is to endow the state space with physical meaning.

Specifically, this could be done as follows:

  • Partition the state vector into subspaces, each corresponding to a category of physical quantities (position, velocity, force, thermodynamics, etc.)
  • Introduce physical constraints into the state transition equations (e.g., conservation of energy, conservation of momentum)
  • Use physical priors to initialize certain parameters (e.g., gravitational acceleration known to be 9.8 m/s²)

Such a "physics-aware" RSSM offers several advantages:

  • Better generalization: Physical laws are universal; policies based on physical modeling transfer more easily to new scenarios
  • Stronger constraints: Physical constraints reduce the degrees of freedom the model needs to learn, accelerating training
  • Better interpretability: Each state dimension has a physical meaning, facilitating debugging and analysis

Of course, this also increases model complexity and requires deep physical understanding of the task. Not every scenario is suited for this approach.

Engineering Implementation Notes

If you plan to implement RSSM yourself, here are some practical considerations from real-world engineering:

1. Network Architecture

The specific RSSM implementation in DreamerV3:

  • Deterministic state h: dimension 1024, updated via a GRU with a 4-layer MLP
  • Stochastic state z: dimension 32 (note: much smaller than h), parameterized Gaussian distribution via a 2-layer MLP
  • Both prior and posterior networks are 2-layer MLPs, outputting mean and log standard deviation

2. Numerical Stability

If the standard deviation of the Gaussian distribution is too small, the KL divergence can explode; if too large, the model cannot make precise predictions. In practice, the standard deviation is typically clamped:

sigma = torch.clamp(sigma, min=1e-4, max=1.0)

3. Gradient Propagation

During imagination training, gradients must be backpropagated through the world model to the actor network. Since imagination trajectories can be long (15 steps), gradient vanishing/exploding is a concern. DreamerV3 addresses this with gradient clipping.

4. Experience Replay

Training data comes from an experience replay buffer. In practice, complete episode sequences are stored, and during training, 64 random sequence segments are sampled. The replay buffer is typically sized at around 1 million steps.

Comparison with Other State-Space Models

To gain a more comprehensive understanding of RSSM, let's compare it with several other common state-space models:

RSSM vs. Classical Kalman Filter

The Kalman Filter assumes linear dynamics and Gaussian noise; RSSM uses neural networks to learn nonlinear dynamics. The Kalman Filter's state transition is matrix multiplication; RSSM uses GRU + MLP. But the core idea is similar: maintain a belief about the state of the environment and update it through observations.

RSSM vs. Transformer

Transformers process the entire history sequence via attention; RSSM compresses historical information through a recurrent state. Transformer computational complexity is O(n²); RSSM is O(n). For robotic tasks requiring long-range memory, RSSM is more efficient. However, Transformers are stronger at capturing long-range dependencies.

RSSM vs. Mamba / S4

Mamba and S4 are newer state-space models that improve expressiveness through selective mechanisms and structured parameterization. They are primarily used for sequence modeling (similar to Transformers), while RSSM focuses on control scenarios. The two approaches are potentially complementary — using Mamba's selective mechanism to improve RSSM's state updates is a direction worth exploring.

Summary

The core contribution of RSSM is that it provides an effective way to simultaneously model the deterministic dynamics and stochastic factors of an environment. Through its dual-track state design, it can handle sequential data like an RNN while expressing uncertainty like a probabilistic model.

In DreamerV3, RSSM has been shown to achieve high-level performance across 55 Atari games with a single set of parameters, and also enables efficient policy learning in robotic manipulation tasks. This demonstrates that the RSSM design captures some essential characteristics of environment modeling.

If you're interested in the implementation of RSSM, I recommend checking out the official DreamerV3 code (searchable on GitHub). Focus on the RSSM class implementation — it's not a lot of code, but the design is elegant.
