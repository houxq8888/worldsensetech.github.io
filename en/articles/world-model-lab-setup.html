Building a World Model Lab from Scratch: A MuJoCo + DreamerV3 Practical Guide

August 5, 2026 · ~15 min read · Tutorial, MuJoCo, DreamerV3, World Models

I've written several theoretical articless about world models — from RSSM math to Sim-to-Real transfer to the VLA comparison. A reader asked: I get the theory, but how do I actually run it?

This article answers that question. I'll walk you through setting up a complete world model experiment environment, step by step from installation to training to visualization. Once you get this running, you'll have a solid foundation for your own experiments.

Our tool stack: MuJoCo (physics simulation) + DreamerV3 (world model) + TensorBoard (visualization). If you need higher-fidelity rendering, you can later swap in Isaac Sim, but MuJoCo is sufficient for getting started.

Tool Selection: Why These Three

MuJoCo: One of the most popular simulation engines in robotics. High physics accuracy, clean API, fast. Open-sourced and free after DeepMind's acquisition in 2021, it's now the de facto standard for robotics learning research and one of the most commonly used benchmarks in continuous control world model research.

DreamerV3: A world model algorithm by Danijar Hafner et al., the third generation of the Dreamer series. It uses RSSM (Recurrent State-Space Model) to learn environment dynamics and trains Actor-Critic policies in imagination space. Open-source with clear documentation — the best starting point for learning world models.

TensorBoard: A general-purpose experiment visualization tool. DreamerV3 outputs training metrics through its logging interface, and TensorBoard reads these logs for visualization. You can view training curves, imagination space visualizations, and agent behavior videos in real-time. Note that DreamerV3 is built on JAX + Haiku, not TensorFlow — TensorBoard is just a general-purpose log viewer and doesn't imply a TensorFlow dependency.

Step 1: Environment Setup

System requirements:

  • OS: Linux (Ubuntu 20.04/22.04 recommended) or macOS. Windows users should use WSL2
  • Python: 3.10 or 3.11 (DreamerV3 has version requirements)
  • GPU: Optional but strongly recommended. NVIDIA GPU significantly accelerates training
  • RAM: 16GB+ recommended

Create a new conda environment:

conda create -n worldmodel python=3.11
conda activate worldmodel

If you have an NVIDIA GPU, install JAX with CUDA support (JAX is DreamerV3's underlying framework). The default pip install jax only installs the CPU version — GPU users need to specify explicitly:

# GPU users (CUDA 12)
pip install "jax[cuda12]"

# For specific CUDA versions, see JAX official docs:
# https://jax.readthedocs.io/en/latest/installation.html

Verify GPU is recognized:

python -c "import jax; print(jax.devices())"

If you see GpuDevice(id=0), GPU is configured correctly. If only CpuDevice(id=0) appears, JAX isn't using the GPU — check your NVIDIA driver and CUDA version compatibility.

Step 2: Install MuJoCo

MuJoCo can now be installed directly via pip — much easier than before:

pip install mujoco

Verify installation:

python -c "import mujoco; print(mujoco.__version__)"

For visual rendering (seeing the robot's 3D view), you'll need a rendering backend. This is where many beginners get stuck — especially on remote servers.

# Install rendering dependencies
pip install mujoco[extras]

# For headless servers without GPU, also install OSMesa
sudo apt-get install libosmesa6-dev

On remote servers or headless machines, you must explicitly set the rendering backend environment variable, or you'll get GLFW errors:

# Server with NVIDIA GPU
export MUJOCO_GL=egl

# Server without GPU
export MUJOCO_GL=osmesa

Add this to your ~/.bashrc to avoid re-setting it each time. Verify GPU status with:

nvidia-smi

Step 3: Install DreamerV3

The official DreamerV3 code is on GitHub. Note that DreamerV3 is not a traditional Python package — its code structure, dependency management, and entry points have changed across versions. For reproducibility, lock to a specific commit:

git clone https://github.com/danijar/dreamerv3.git
cd dreamerv3

# Lock to a verified commit (avoids future version changes breaking commands)
git checkout 60b6 example_commit_hash

pip install -r requirements.txt

For MuJoCo environments, install the DeepMind control library:

# DeepMind Control Suite (includes MuJoCo predefined tasks)
pip install dm-control

Note: Some online tutorials write pip install dm-control-suite — this package doesn't exist. The correct package name is dm-control.

Understanding the Code: Not a Black Box

Before running experiments, take a look at DreamerV3's code structure so you know where the core components live. Otherwise you're just running a black box:

dreamerv3/
├── dreamerv3/
│   ├── agent.py          # Agent logic (Actor, Critic)
│   ├── models.py         # World model (RSSM core is here)
│   ├── networks.py       # Neural network definitions
│   └── configs.py        # Hyperparameter configs
├── embodied/
│   ├── envs/             # Environment wrappers (incl. DM Control adapter)
│   └── main.py           # Training entry point
└── requirements.txt

Key locations:

  • RSSM (Recurrent State-Space Model): Implemented in models.py — the core of the world model, responsible for encoding observations and predicting future states
  • Actor: In agent.py, generates actions in imagination space
  • Imagination training: Also in agent.py — the Actor samples latent states from RSSM, imagines multiple trajectories, and optimizes the policy
  • Replay Buffer: Stores real interaction experience data

Knowing these locations, you can go directly read how RSSM's forward pass is implemented — more intuitive than reading the paper.

Step 4: Run Your First Experiment

Let's start with a relatively simple task: Cartpole Balance — teaching a cart to keep a pole upright. This task has low action dimensionality and converges quickly — ideal for verifying your setup.

Before running, check which task names the current repository supports. Different versions may use different naming (e.g., dmc_walker_walk vs. dm_control_walker_walk). Check first:

# Check available tasks and configs
python embodied/main.py --help

After confirming the task name, run training. The entry point varies by version — it could be dreamerv3/main.py, embodied/main.py, or python -m dreamerv3.main. Use whatever matches your locked version's structure:

python embodied/main.py \
  --logdir ~/logdir/wm_cartpole_balance \
  --configs defaults dm_control \
  --task dmc_cartpole_balance \
  --steps 1e6

Parameters:

  • --logdir: Log and model save path
  • --configs: Preset configurations (defaults + dm_control, exact names depend on repository version)
  • --task: Specific task name — cartpole_balance is the cart balancing task
  • --steps 1e6: Train for 1 million steps

Training time depends on your hardware. A consumer-grade GPU (RTX 3060+) takes roughly tens of minutes to a few hours. Without GPU, CPU-only training could take a day or more. Overall range: tens of minutes to tens of hours.

To quickly verify the pipeline works, use fewer steps:

python embodied/main.py \
  --logdir ~/logdir/wm_test \
  --configs defaults dm_control \
  --task dmc_cartpole_balance \
  --steps 1e4

10K steps takes just a few minutes on GPU — enough to verify the pipeline.

After Cartpole Balance works, gradually increase difficulty:

# Recommended difficulty progression
dmc_cartpole_balance    # ⭐ Beginner
dmc_walker_stand        # ⭐⭐ Standing
dmc_cheetah_run         # ⭐⭐⭐ Running
dmc_walker_walk         # ⭐⭐⭐⭐ Walking (multi-joint coordination)
dmc_humanoid_walk       # ⭐⭐⭐⭐⭐ Humanoid walking (hardest)

Step 5: Visualize Training

Open another terminal and launch TensorBoard:

tensorboard --logdir ~/logdir/wm_cartpole_balance --port 6006

Open http://localhost:6006 in your browser. Key metrics to watch (note: exact metric names vary by version — these are the common categories):

1. Episode Return / Score: The core metric — cumulative reward in the real environment. Should increase over training. May appear as episode/return, train/return, or eval/score depending on version.

2. Imagination Space Evaluation: Policy performance evaluated in imagination space. A large gap between imagination evaluation and real-environment return suggests world model accuracy issues.

3. Model Loss / Prediction Loss: RSSM's composite loss, typically including observation reconstruction loss, reward prediction loss, and continuation prediction loss. Decreasing values indicate improved observation modeling, but this does not directly imply improved control — low reconstruction error doesn't mean good control performance.

4. Actor Loss / Policy Loss: Policy network optimization loss, reflecting how well the Actor is learning in imagination space.

5. Video Playback: In the Images tab, compare agent behavior in real vs. imagined environments — a direct look at imagination quality.

Advanced: Observing the World Model's "Imagination"

This article is about world models, but so far we've mainly been looking at policy training. The world model's most fundamental capability is imagination — given a current state, predicting what will happen next. We should observe this directly.

DreamerV3's RSSM can perform imagination rollout:

  1. Encode the current latent state from real observations
  2. RSSM autonomously rolls forward multiple steps from this state
  3. Each step predicts: future frames, reward, and termination

In TensorBoard's Images tab, you can see videos generated from imagination space. For a more direct approach, do rollout analysis in code:

# Pseudocode: imagination rollout
# From a real state, let the world model "imagine" the future
latent_state = rssm.encode(real_observation)
for step in range(horizon):
    action = actor(latent_state)
    next_latent, predicted_obs, predicted_reward = \
        rssm.imagine(latent_state, action)
    # Compare predicted_obs vs real observations

This is the most critical step for understanding Dreamer. If imagined frames increasingly resemble real frames, the world model is indeed learning environment dynamics. If imagined frames are blurry or distorted, the model needs more training, or the task exceeds the current model capacity.

Step 6: Analyze Training Output

After training, the logdir structure looks like:

~/logdir/wm_cartpole_balance/
├── events.out.tfevents.*    # TensorBoard logs
├── configs.yaml              # Training config
├── variables.pkl             # Model weights
└── metrics.json              # Metric records

Load metrics.json with Python for analysis (metric key names vary by version — use actual output):

import json
import matplotlib.pyplot as plt

with open('~/logdir/wm_cartpole_balance/metrics.json') as f:
    metrics = [json.loads(line) for line in f]

# Metric keys vary by version — print available keys first
print(metrics[0].keys() if metrics else "No data")

steps = [m['step'] for m in metrics]
# Common keys: episode/return, eval/return, train/return
returns = [m.get('episode/return', m.get('eval/return', 0)) for m in metrics]

plt.plot(steps, returns)
plt.xlabel('Training Steps')
plt.ylabel('Episode Return')
plt.title('DreamerV3 on Cartpole Balance')
plt.savefig('training_curve.png')
plt.show()

Common Issues

Issue 1: MuJoCo rendering error — "GLFW error"

Set environment variable for offscreen rendering:

export MUJOCO_GL=egl     # with GPU
# or
export MUJOCO_GL=osmesa  # without GPU

Issue 2: Training is very slow

Likely causes: no GPU (CPU-only is 10x+ slower), batch size too large, or insufficient environment parallelism. If you have a GPU, verify JAX correctly detects CUDA (check with jax.devices()).

Issue 3: Training return not increasing

Try a simpler task first (e.g., reach task). DreamerV3's default hyperparameters are well-tuned for most MuJoCo tasks — usually no need to modify.

Issue 4: Out of memory (OOM)

Reduce replay buffer size in configs: buffer_size=1e5 (default is larger).

Next Step: From MuJoCo to Isaac Sim

MuJoCo is great for algorithm validation, but rendering realism is limited. If you need more realistic visual inputs (e.g., training a robot to recognize objects from camera feeds), you can upgrade to NVIDIA Isaac Sim.

Isaac Sim, built on the Omniverse platform, provides physically accurate simulation with high-fidelity rendering. The API differs from MuJoCo, and while DreamerV3's training pipeline is the same, migrating from MuJoCo to Isaac Sim involves more than just writing an environment wrapper. Differences you'll need to handle include:

  • Observation design: Isaac Sim's visual output format, resolution, and camera parameters differ from MuJoCo — requires adaptation
  • Camera latency: High-fidelity rendering introduces additional latency, potentially affecting training stability
  • Physics timestep: The two engines differ in simulation frequency and integration accuracy — may need action repeat adjustment
  • Action scaling: Action space ranges and semantics may differ — requires recalibration
  • Domain randomization: Randomization strategies need to be redesigned for Sim-to-Real transfer

I'll cover this advanced topic in a future article. For now, get MuJoCo + DreamerV3 running and understand the training pipeline — that's what matters most.

Optional: One-Click Docker Setup

If you've spent too much time on local environment setup (CUDA versions, MuJoCo rendering, JAX GPU, etc.), consider using Docker for environment consistency. Here's a basic Dockerfile example:

FROM nvidia/cuda:12.2.0-runtime-ubuntu22.04

RUN apt-get update && apt-get install -y \
    python3.11 python3-pip libosmesa6-dev \
    libgl1-mesa-glx libglfw3-dev

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
RUN pip install "jax[cuda12]" mujoco dm-control

COPY . .
CMD ["python", "embodied/main.py", \
     "--logdir", "/app/logdir", \
     "--configs", "defaults", "dm_control", \
     "--task", "dmc_cartpole_balance"]

Docker ensures complete reproducibility — no more "works on my machine" issues. Especially useful for team collaboration and paper experiment reproduction.

Summary

Today we built a complete world model experiment environment: MuJoCo for physics simulation, DreamerV3 for world model training, TensorBoard for visualization. The whole process from installation to running the first experiment takes about 30-60 minutes (depending on network speed and whether you use Docker).

Once running, try:

  • Progressively increasing task difficulty (walker stand → cheetah run → walker walk → humanoid walk)
  • Running imagination rollouts to observe the world model's "imagination" quality
  • Adjusting hyperparameters and observing imagination quality changes
  • Comparing DreamerV3's sample efficiency with traditional RL (e.g., PPO)
  • Adding language conditioning to explore language-grounded world models

Practice beats theory. Running one experiment teaches you more than reading ten papers.
